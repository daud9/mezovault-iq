# Bridge Tracker and MUSD x402 Payment Links

## Bridge Status Tracker

The app’s Bridge Status Tracker page is a **read-only tracker** for MEZO NTT transfers that originate on Mezo Testnet. It queries the documented Wormholescan Testnet `GET /api/v1/operations` endpoint using the official Mezo Testnet Wormhole transceiver address and `pageSize=100`, then compares the entered source transaction hash locally. The transaction hash is not sent to Wormholescan, and the lookup does not connect a wallet or submit a transaction.

Status labels describe only what the index contains:

- **Source operation indexed:** a source record is present.
- **Attestation available; destination not indexed:** Wormholescan reports a VAA but no destination transaction record.
- **Destination execution indexed:** a target-chain record is present; this is an index status, not a separate finality guarantee.
- **Not found:** the source hash did not match the latest 100 indexed records. This is inconclusive: it may be an unrelated transaction, outside the recent page, or not indexed yet.

Mezo’s Testnet bridge guide describes MEZO transfers through Wormhole NTT and says to wait for confirmation on both chains. It does not document a Testnet rescue, refund, or manual-claim action. The page therefore presents no supported recovery action and warns users not to retry just because a lookup is missing or pending.

This Testnet NTT tracker is separate from Mezo’s **Mainnet native-BTC bridge-in**. Mezo says native BTC deposits closed on October 13, 2026; deposits started before then can be checked through Mezo’s [tracking guide](https://mezo.org/docs/users/mainnet/track-your-native-bitcoin-deposit/) and the [tBTCScan deposits page](https://tbtcscan.com/deposits).

Sources: [Mezo Testnet MEZO Bridge](https://testnet.mezo.org/docs/de/docs/users/mezo/mezo-bridge/), [official Mezo Testnet NTT deployment manifest](https://github.com/mezo-org/ntt-bridge-mezo-testnet/blob/main/deployment.json), and [Wormholescan API guide](https://wormhole.com/docs/products/messaging/guides/wormholescan-api/).

## Gasless MUSD Pay Links

Mezo Testnet x402 uses CAIP-2 network `eip155:31611`, MUSD at `0x118917a40FAF1CD7a13dB0Ef56C86De7973Ac503` (18 decimals), and the facilitator endpoint listed in Mezo's x402 documentation, `https://facilitator.vativ.io`. This code uses that endpoint as a hard-coded server-side constant; it is not buyer-controlled or environment-overridable. The buyer signs an EIP-712 authorization in their own wallet; the facilitator verifies, submits and settles it, paying native BTC gas. This is a payment for a server-backed resource, not a general gasless ERC-20 transfer or ERC-4337 paymaster. The documentation supports the endpoint's use but does not establish who owns or operates it.

The original hosting instructions served only `dist`, which could not issue and settle recipient-specific x402 requirements. The repository now declares a dynamic Deno Deploy runtime in `deno.json`, with `server/main.ts` as the entrypoint; Express serves the SPA and merchant API. Deno Deploy’s official runtime docs describe a standard Deno runtime with npm dependencies, and Deno’s Express guide and Deploy examples use `app.listen`. A `deploy` block in `deno.json` takes precedence over dashboard build/runtime settings, while the app directory remains a dashboard setting.

A seller creates a reusable 30-day link after signing an off-chain message binding their recipient wallet, fixed MUSD amount, Testnet, issue time and nonce. The server verifies that signature and throttles a recently seen nonce in a process-local memory window; this is best-effort, not a durable or cross-instance one-time guarantee. It then returns a stateless HMAC token and does not durably store link/seller records, buyer identity, payment payloads, or settlement state. The same link can accept multiple separately authorized payments before expiry; the app has no paid/consumed status and does not disable a link after a reported settlement. Exact same-authorization replay behavior depends on the live facilitator and is not established here. Amounts are exact decimal strings in the range 0.001–1,000 MUSD, and the server uses the SDK’s default Testnet MUSD asset rather than a browser-supplied token address. The share token is placed in the URL fragment, is not sent with the initial page request, and is passed to the merchant only in the checkout POST body.

The browser fetches the resource’s HTTP 402 requirement and validates its exact scheme, network, MUSD contract, recipient, amount, resource URL, and maximum 300-second authorization lifetime before presenting the wallet action. In the pinned `@x402/evm` 2.30.0 registry, a dollar-string price on `eip155:31611` resolves to MUSD `0x118917a40FAF1CD7a13dB0Ef56C86De7973Ac503`, with 18 decimals and `assetTransferMethod: permit2`; the configured facilitator’s current `/supported` response advertises this Testnet MUSD address for x402 `exact`, Permit2, and EIP-2612 gas sponsorship. Mezo's official guide documents MUSD as Permit2 plus EIP-2612. The exact client uses Permit2, not `transferWithAuthorization`, and the application test checks the actual generated `PAYMENT-REQUIRED` asset. The Mezo Testnet explorer identifies the address as Mezo USD (MUSD) but the returned contract page did not expose a verified ABI; direct RPC reads were blocked with HTTP 403 from this environment. Therefore deployed ABI behavior and a live buyer authorization remain unverified; docs and facilitator metadata are not an on-chain execution test.

The buyer signs through the connected wallet; the app exposes typed-data signing and read-only contract calls to the x402 client, not transaction sending. The server's `processHTTPRequest` verifies the authorization and returns payment requirements; the app checks scheme, network, asset, recipient and amount before calling the separate `processSettlement`. Thus `payment_terms_mismatch` is a pre-settlement rejection, not evidence that this guard ran after funds moved. A different case is possible: settlement can report success, then its network/amount/hash receipt can mismatch. The server returns a valid transaction hash and network when available, returns no paid confirmation, and warns that payment may already have occurred. Failed settlement remains HTTP 402; a mismatched receipt fails closed. No private keys or buyer authorizations are held or signed by the server.

Before opening the wallet authorization flow, the browser stores a pending-attempt marker keyed by a SHA-256 hash of the link token. A marker may therefore represent an interrupted prompt that never reached the server as well as a submitted payment with an ambiguous result. The app keeps the link in a status-only state after reload and offers an explorer link, not a new signature. This marker exists only in that browser's local storage: it is not an authoritative payment record, is not shared across devices, can be removed by clearing browser data, and does not query facilitator or chain status automatically. If no usable transaction hash was returned, the buyer must check wallet activity and the Mezo Testnet explorer manually before making any further payment.

Before enabling pay links in a deployment, set `PAY_LINK_SECRET` as a server-side secret in each environment that should allow link creation. It must contain at least 32 random bytes; do not expose it as a `VITE_` variable or commit it. The facilitator endpoint is currently fixed in code; `/api/pay-links/status` reports secret/configuration and the endpoint URL, not live health or settlement capability. The bounded in-memory limiter holds transient IP, recipient, and per-link keys, caps the map at 5,000 entries, and may evict active windows under high key diversity. Limits are per server process/instance, are not shared across Deno Deploy instances, and reset on restart, so they are best-effort throttles rather than global quotas or replay guarantees. No payment request bodies or buyer/seller records are durably stored.

The Mezo quickstart pins x402 2.16.0 for its demo, while Mezo’s reference lists Testnet support from `@x402/evm` 2.10.0. This implementation pins the updated 2.30.0 `@x402/core` and `@x402/evm` packages, whose installed default registry maps `eip155:31611` to Mezo Testnet MUSD. It avoids the universal browser paywall bundle and Express x402 adapter; the browser uses the framework-neutral client and the server uses the x402 core HTTP resource server. Integration tests mock the wallet signer and facilitator. They make no live signed verification or settlement and cannot establish deployed token ABI, settlement behavior, or finality.
