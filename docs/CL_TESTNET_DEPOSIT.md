# Mezo Testnet CL Position Deposit

The `/app/cl-planner` route now includes a separate wallet-confirmed flow to mint a new Slipstream CL position NFT. The planner and `/app/cl-positions` monitor remain read-only. The deposit flow is locked to Mezo Testnet chain `31611`; it does not add a backend signer or support private-key/seed-phrase input.

## Verified deployment and call

The [official Mezo Pools documentation](https://mezo.org/docs/developers/features/mezo-pools/) lists the Testnet CL Factory at `0x7B61BC8Aa460476d142F1CD107A47297002f69ff` and Nonfungible Position Manager at `0x9B753e11bFEd0D88F6e1D2777E3c7dac42F96062`. The [Testnet explorer’s manager page](https://explorer.test.mezo.org/address/0x9B753e11bFEd0D88F6e1D2777E3c7dac42F96062?tab=contract) reports exact-match verified source, `NonfungiblePositionManager`, Solidity `0.7.6+commit.7338295f`, optimization enabled with 100 runs, and constructor arguments whose first address is the same Factory.

The deployed-source reference is cross-checked with Slipstream’s [`INonfungiblePositionManager`](https://github.com/velodrome-finance/slipstream/blob/main/contracts/periphery/interfaces/INonfungiblePositionManager.sol) and [`NonfungiblePositionManager` implementation](https://github.com/velodrome-finance/slipstream/blob/main/contracts/periphery/NonfungiblePositionManager.sol). `MintParams` is the static tuple `(address token0,address token1,int24 tickSpacing,int24 tickLower,int24 tickUpper,uint256 amount0Desired,uint256 amount1Desired,uint256 amount0Min,uint256 amount1Min,address recipient,uint256 deadline,uint160 sqrtPriceX96)`. The canonical mint signature selector is `0xb5007d1f`. `mint` returns `(tokenId, liquidity, amount0, amount1)`.

The verified implementation calls `factory.createPool(...)` only when `sqrtPriceX96 != 0`; the flow sets it to zero and independently checks the existing Factory mapping, so it never requests pool creation or initialization. The [Slipstream liquidity management callback](https://github.com/velodrome-finance/slipstream/blob/main/contracts/periphery/base/LiquidityManagement.sol) pays with `payer: msg.sender`; [`PeripheryPayments.pay`](https://github.com/velodrome-finance/slipstream/blob/main/contracts/periphery/base/PeripheryPayments.sol) uses `safeTransferFrom` for that payer. Therefore, a wallet-held token needs an ERC-20 allowance to the position manager. Approvals are separate wallet actions for the exact desired raw-unit amount, never unlimited.

The fee shown is read from the Factory’s live `getSwapFee(pool)` method, using the [Slipstream Factory interface](https://github.com/velodrome-finance/slipstream/blob/main/contracts/core/interfaces/ICLFactory.sol). That interface describes this value in pips (`1e-6`) and notes that it accounts for default and dynamic fees. Tick spacing is read from the selected pool; both are displayed before any wallet request. The fee is informative and is not an argument to `mint`.

The earlier project live-code check at Testnet block `16,734,912` recorded the manager runtime as 23,510 bytes with Keccak-256 `0x071af6bf4d327858890389ca0f62bad9731e3f497eae1d6a50cac442a1d44030`; see [`MEZO_CONTRACT_VERIFICATION.md`](./MEZO_CONTRACT_VERIFICATION.md). During this implementation, the build sandbox’s direct JSON-RPC POST to the configured Testnet endpoint was denied, so no new live block/hash smoke check was made here. Runtime preflight must still pass against current configured Testnet state before the wallet action is enabled.

## User review and execution gates

1. Connecting or switching networks is always an explicit button action. The flow makes no transaction request on page load, connection, refresh, or planner input changes.
2. “Prepare exact deposit review” performs read-only calls at one Testnet block. It checks chain ID, deployed code for the manager/factory/pool/tokens, the manager’s Factory getter, the selected pool’s canonical token order and spacing, the Factory `getPool(address,address,int24)` mapping, live slot/tick/liquidity, token decimals, live swap fee, wallet balances and allowances.
3. The review shows the pool address and pair, fee and tick spacing, entered price range plus rounded contract ticks, current range status, both tokens’ exact human and raw desired amounts, minimum amounts, wallet/recipient, network, deadline, manager, exact mint signature and calldata, and native transaction value `0`. User-entered budget remains denominated in token1, not USD.
4. Desired amounts come from the planner’s live-state calculation and are floored to token base units. The budget guard values token0 raw units as token1 raw units using `sqrtPriceX96² / 2¹⁹²`; this is already a raw-unit ratio, so no additional token-decimal multiplier is applied. It rounds token0 value upward and scales/caps the split if raw-unit rounding would exceed the entered token1 budget at the checked spot price. The chosen 0.5%, 1% or 2% tolerance sets each minimum to `floor(desired * (10000 - bps) / 10000)`. Amounts are maxima; any unused tokens remain in the wallet.
5. Before an approval prompt, the exact `approve(manager, amount)` or any separate zero-reset call is estimated and simulated. Only the first missing allowance is handled at a time. After its receipt is confirmed, the user must prepare a new review before another approval or mint.
6. Before a mint prompt, the exact call is re-simulated with fresh pool mapping, fee, tick, wallet balances and allowances. A changed fee/tick, expired review/deadline, inadequate allowance or balance, failed simulation, or invalid simulated amounts blocks the wallet request. The plan expires after three minutes; a simulation is accepted for a wallet action for 30 seconds.
7. The connected injected wallet is the only signer and must still match the reviewed account and chain. The UI labels `eth_call` as simulation, never as a transaction. A transaction is described as successful only after `eth_getTransactionReceipt` returns status `0x1`; a missing receipt remains pending/unconfirmed and status `0x0` is shown as reverted.

The implementation creates only a new position through `mint` plus exact ERC-20 approvals. Increase/decrease liquidity, collect, burn, gauge stake, reward claim, NFT transfers, and mainnet writes are outside this flow.

## Tests

`src/lib/clDeposit.test.ts` uses a fake JSON-RPC client to test tuple encoding (including negative signed ticks), exact approvals, 18/6 and 6/18 decimal conversions, token1 budget caps, minimum amounts, live key/fee reads, balance/network failure, simulation return bounds, stale review and fee-change rejection. The fake client rejects any unrecognized RPC method, including `eth_sendTransaction`. Tests do not broadcast a transaction or establish current live state.
